# Dashboard deviations

- Task 1 — the "migration 4" test in db.test.ts now asserts `SCHEMA_VERSION >= 4` instead of `=== 4`, and the upgrade test in digest-store.test.ts also drops the three new tables when rewinding to version 1 — both replay or pin older schema versions, so migration 5 broke them (same fix Part 5 used).
- Task 2 — `findToken` in oauth/store.ts now also selects `g.client_name` and returns it as `grant.clientName`, so `checkCredential` can put `clientName` on OAuth credentials — the existing join already reached the grant row, so one extra column was the smallest change.
- Task 2 — added `logActivitySafe` (try/catch around `logActivity`, errors go to the server log) in activity.ts; the brief asked each call to be wrapped, one shared helper does it.
- Task 2 — existing tests that pinned `checkCredential`'s exact result (tokens.test.ts) and the MCP caller (http.test.ts, mcp.test.ts `canSave: true`) were updated for the new `id`/`label`/`clientName`/`actor` fields.
- Task 3 — the existing "uploads and prints a summary" cli test now expects the extra `POST /api/sync-runs` request, and the sync.test.ts fake server records reports in a separate `reports` list so existing `sent` assertions are unchanged — every real sync now sends a report.
- Task 3 — a failed report is returned as an optional `reportError` on `SyncReport` and printed by `printReport` (one stderr line starting "Note: could not report this run"), rather than thrown — keeps `runSync` callers and the exit code unaffected.
- Task 4 — `WebConfig` gained `publicOrigin: string | null` — the controller's Origin check on every authenticated POST needs the configured public origin, and neither given interface (`WebConfig`, `WebCtx`) carried it; `WebConfig` was the smaller change. A present `Origin` that differs from it answers 403; when it is null (no `PUBLIC_URL`, tests) only the csrf check applies.
- Task 4 — extracted `drainBody(res)` from `send()` in http.ts and exported it, so the web layer's early answers (403, 429, redirects) discard an unread request body the same way and cannot stall a kept-alive connection.
- Task 4 — web/html.ts also exports `sendPage`, `redirectTo` and `forbiddenPage` besides `escapeHtml`/`securityHeaders`/`signInPage` — the shell writer and the redirect helper are what carry the security headers, so every answer gets them from one place.
- Task 4 — the "bare address" tests in http.test.ts now assert the signed-out contract: `GET`/`HEAD /` answer 302 `/login` and `POST /` answers 403 (was 404), per the controller's ruling that `POST /login` is the only POST allowed without a session.
- Task 4 — a signed-in `GET /activity`, `/projects`, `/projects/<key>` or `/sign-ins` still falls through to the JSON 404 until Tasks 5-8 add those pages; the signed-out 302 to `/login` already covers all of them, which is what Review Focus 1 pins.
- Task 4 (fix round 1) — `secureCookies` is now `publicUrl?.startsWith('https://')` (the pure, tested `secureCookiesFor` in web/routes.ts) rather than "unset or starts with `http://localhost`" as the plan worded it: `parsePublicUrl` also accepts `http://127.0.0.1` and `http://[::1]`, and on any plain-http origin the browser drops a `Secure` cookie, so sign-in would have failed silently there. All three loopback forms now omit `Secure`.
- Task 4 (fix round 1) — `POST /login` also gets the Origin check (a present `Origin` that is not the public origin answers 403 before the code is read), so a hostile page cannot spend the owner's ten tries and have the limiter block their address. The plan only asked for csrf on authenticated actions; `/login` has no session to carry a csrf value.
- Task 4 (fix round 1) — the POST branch of `handleWeb` now claims only `/login`, `/logout`, `/sign-ins/disconnect` and the page paths, and returns false for anything else, so a POST to an unknown `/api/` or `/oauth/` path reaches the JSON 404 without the session cookie being looked up at all.
- Task 5 — Google Fonts are loaded with an `@import` at the top of `app.css`, not a `<link>` in each page head — the existing signed-out tests (`http.test.ts`, `web-session.test.ts`) reject any two-digit run in the sign-in page, and the font URL's weights (`400;500`) tripped them; the CSP already allows googleapis for styles.
- Task 5 — `app.js` is loaded in the head without `defer` (it waits for DOMContentLoaded for everything but the theme) — so a stored theme applies before first paint.
- Task 5 — assets use `Cache-Control: public, max-age=604800` (7 days), not a year — the URLs are not content-hashed, so a long max-age would pin stale CSS after a deploy.
- Task 6 — `Problem` gained an optional `at?: string` besides `kind`/`text`/`ref` — the failed-summary, state-retry, sync and backup lines all carry a time, and the global rule says every time is rendered as `<time datetime="ISO">`, which baking the timestamp into `text` would break. `text` stays plain, unescaped prose; `pages.ts` escapes it once and appends the `<time>` element.
- Task 6 — refused summaries are rendered in their own "Notices" box below the Problems box, not inside it — the Problems box is shown "only when there are problems", and a refused summary is not one, so with only refused summaries the page is Healthy and has no Problems box.
- Task 6 — `computeHealth` splits the sync rule into kinds `sync-failing` (last run had errors) and `sync-quiet` (no run for more than three days, or no run at all with the server up more than three days); one kind per rule keeps the per-rule tests exact.
- Task 6 — "summaries are off" is only raised while at least one summary is pending (as the brief words it), and "pending for more than 1 hour" is measured from the digest row's `updated_at`, which `markDigestPending` sets — there is no separate queued-at column.
- Task 6 — `overviewPage(db, cfg, now, csrf)` takes its arguments explicitly rather than a `WebCtx`, so `pages.ts` does not import a value from `routes.ts` while `routes.ts` imports the page (type-only import one way).
- Task 7 — `countActivity(db, {direction?})` was added to activity.ts (outside the brief's Files list): `listActivity` returns rows only, so without a count a `?page=9999` could only land on an empty page rather than the last one, which "clamp to 1 or last" asks for.
- Task 7 — the activity table's What column now shows a plain name per action (`read page`, `search`, `note`, `deleted`, `sync`, `project list`, `read session`, and `N sessions` for uploads) instead of the stored MCP tool name, through one row renderer shared by the Overview and the Activity page; the Task 6 assertion in web-overview.test.ts that counted ten `get_project` strings now counts ten `read page` strings.
- Task 7 — upload rows are folded only within the 50 rows of the page being rendered, never across a page boundary, and each row is measured against the oldest row already folded in (a gap-based run), so a steady stream of uploads a minute apart stays one line.
- Task 7 — `/activity` reads its `?direction=` and `?page=` from `req.url` inside `handleWeb` rather than `handleWeb` taking a new query argument; `path` in http.ts is `pathname` only, and this kept the controller's signature (and Task 8's POST paths) unchanged.
- Task 7 — a project page lists 10 recent sessions and notes (`get_project`'s `sessions` argument); the MCP default is 5, which is short for a full-width page.
- Task 7 — `/projects/` with an empty segment, a segment holding a real slash (`/projects/a/b`), a malformed escape (`/projects/%zz`) and an unknown key all answer the same plain 404 "No such project" page inside the signed-in shell, with the usual CSP and security headers; `/nope` still falls through to the JSON 404.
- Task 7 (fix round 1) — the pager hrefs go through `escapeHtml`, so the query separator is written `&amp;page=2` rather than a bare `&` inside an attribute; the unfiltered links are unchanged.
